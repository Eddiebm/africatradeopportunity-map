# Deployment

TradeSafe Africa runs on Cloudflare Workers via [vinext](https://github.com/cloudflare/vinext)
(Next.js reimplemented on Vite), with Cloudflare D1 for relational data and
R2 for private documents. Configuration lives in `wrangler.jsonc` at the
repo root — there is no `.openai/hosting.json` or other hidden config
source; everything a deploy needs is either in that file or set as a
Cloudflare secret / GitHub Actions secret.

## 1. Local development

```bash
npm ci
cp .dev.vars.example .dev.vars   # then edit SESSION_SECRET (see below)
npm run cf-typegen               # generates worker-configuration.d.ts from wrangler.jsonc
npm run db:migrate:local         # applies drizzle/*.sql to a local Miniflare D1
npm run dev                      # vinext dev — http://localhost:3000
```

Generate a real `SESSION_SECRET` for `.dev.vars`:

```bash
openssl rand -base64 32
```

`.dev.vars` is gitignored — never commit it. `worker-configuration.d.ts` is
also gitignored and regenerated (`npm run cf-typegen`) whenever
`wrangler.jsonc` changes; run it again if TypeScript starts complaining
about missing `env.DB` / `env.BUCKET` / `env.SESSION_SECRET`.

## 2. Test database setup

Tests that touch D1 run against Miniflare's local SQLite, provisioned the
same way as local dev:

```bash
npm run db:migrate:local
```

Re-run this after adding a new migration (`npm run db:generate` following a
`db/schema.ts` change) — migrations are additive and idempotent, safe to
re-apply.

## 3. Applying migrations

Migrations are plain SQL files under `drizzle/`, generated by
`drizzle-kit` from `db/schema.ts` (never hand-edit a file inside
`drizzle/meta/`; run `npm run db:generate` after every schema change and
commit the generated `.sql` + `meta/*.json` together).

```bash
npm run db:migrate:local     # local Miniflare D1 (dev/test)
npm run db:migrate:remote    # the real D1 database this wrangler.jsonc points at
```

`db:migrate:remote` requires you to be authenticated (`wrangler login` or
`CLOUDFLARE_API_TOKEN`) and for `wrangler.jsonc`'s `database_id` to point at
a real, provisioned database (see step 5).

## 4. Building

```bash
npm run build
```

Runs `cf-typegen` then `vinext build` (multi-environment: RSC + SSR +
client). Fails loudly if `wrangler.jsonc` is missing or malformed — there
is no silent fallback.

## 5. First-time Cloudflare setup (one-time, per environment)

Nothing in this repo can provision real Cloudflare resources for you — an
account owner has to run these once:

```bash
wrangler login
# or, non-interactively (CI): set CLOUDFLARE_API_TOKEN
#   (dash.cloudflare.com/profile/api-tokens -> "Edit Cloudflare Workers" template)

wrangler d1 create tradesafe-africa-db
# -> paste the returned database_id into wrangler.jsonc (d1_databases[0].database_id)

wrangler r2 bucket create tradesafe-africa-documents

wrangler secret put SESSION_SECRET
# paste the output of: openssl rand -base64 32

wrangler whoami   # confirms the account id; set CLOUDFLARE_ACCOUNT_ID or
                  # add "account_id" to wrangler.jsonc if it's ambiguous
```

Repeat `d1 create` / `r2 bucket create` / `secret put` for the `preview`
environment (`--env preview`) if you want an isolated preview database
rather than sharing production data with preview deploys.

Then apply migrations to the real database:

```bash
npm run db:migrate:remote
```

## 6. Preview deployment

```bash
npm run preview   # vinext deploy --preview  (deploys to wrangler.jsonc's "preview" env)
```

## 7. Production deployment

```bash
npm run deploy    # vinext deploy
```

CI (`.github/workflows/ci.yml`) runs lint, typecheck, test and build on
every push/PR, and only deploys to production on `main` after all of those
pass — see that workflow file for the exact gating. Production deploys
need `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` set as GitHub
Actions repository secrets.

## 8. Rollback

Cloudflare Workers keeps deployment history. To roll back to the previous
version:

```bash
wrangler deployments list          # find the deployment id to roll back to
wrangler rollback [deployment-id]  # omit the id to roll back to the previous one
```

A rollback reverts the Worker code only — it does **not** revert D1
migrations. If a bad deploy shipped a destructive migration, the code
rollback plus a hand-written reverse migration (or a restore from a D1
backup — `wrangler d1 export` before any destructive migration is strongly
recommended) is the real recovery path. This is why the working rules for
this project forbid destructive schema changes without a migration *and
backup* plan: `wrangler d1 export tradesafe-africa-db --remote --output backup.sql`
before applying anything that drops or renames a column or table.

## Secrets this app currently needs

| Secret | Set with | Used by |
|---|---|---|
| `SESSION_SECRET` | `wrangler secret put SESSION_SECRET` | `lib/auth/session.ts` — signs the session cookie |

No payment, identity-verification, or email-provider credentials are
wired yet (see `lib/email.ts` and `docs/AUDIT.md`) — connecting a real
provider means adding its secret here and to this table.
